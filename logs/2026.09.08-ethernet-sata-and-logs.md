# AETHER Log #42 – When Systems Misbehave

**Date:** September 8, 2026

It has been several weeks since the last AETHER log.

I am aware.

AETHER has not disappeared, and the lab has not been abandoned. The environment has simply reached a point where not every week produces a new server, service, or major architectural change.

That is probably a good thing. It has been a period of peace with no trouble, I've been able to step away from the lab a bit.

The previous phase focused heavily on the transition from building infrastructure to operating it. This phase provided a less glamorous but equally useful reminder of what operating infrastructure actually involves:

> **Sometimes things just break.**

Two unrelated problems appeared on the same day: an intermittent Ethernet failure on my Windows desktop and a much more interesting boot and storage problem on Nora following a power outage.

Neither required deploying anything new.

Both required investigating what already existed.

---

## An Intermittent Ethernet Failure

My Windows 10 desktop experienced a problem that has occurred occasionally in the past: the wired Ethernet connection suddenly stopped working.

The Ethernet cable itself was known to be good, and historically restarting the computer has restored connectivity.

Rather than immediately rebooting, I attempted to reset the network adapter from within Windows by disabling and re-enabling the Realtek PCIe GbE Family Controller.

That did not work.

A full system restart did.

Because the problem had now disappeared, the next question was whether Windows had recorded what happened before the reboot.

It had.

Event Viewer contained the following message repeatedly over approximately 15 minutes:

> The network interface "Realtek PCIe GbE Family Controller" has begun resetting. There will be a momentary disruption in network connectivity while the hardware resets. Reason: The network driver detected that its hardware has stopped responding to commands.

Windows reported that the interface had reset **21 times** since initialization.

This changed the problem from:

> The Internet stopped working.

into something much more specific:

> The Realtek Ethernet controller stopped responding to driver commands, Windows repeatedly attempted to reset the hardware, and those resets failed to restore stable connectivity.

---

## Finding a Decade-Old Driver

The next step was to inspect the network adapter itself.

The hardware was identified as:

```text
Realtek PCIe GbE Family Controller

PCI\VEN_10EC&DEV_8168&SUBSYS_859E1043&REV_11
````

The installed driver was then recorded:

```text
DeviceName:       Realtek PCIe GbE Family Controller
DriverVersion:    9.1.410.2015
DriverDate:       April 9, 2015
Manufacturer:     Realtek
```

The driver was more than eleven years old.

That does not prove that the driver caused the failure. The Ethernet problem occurs rarely, and old drivers can continue working correctly for years.

However, the evidence provided a reasonable troubleshooting path:

1. The controller became unresponsive.
2. Windows repeatedly attempted hardware resets.
3. Resetting the adapter manually did not restore connectivity.
4. A complete reboot did.
5. The controller was using a driver from 2015.

The driver was therefore updated before making any additional changes to power management, Energy Efficient Ethernet, duplex configuration, or other adapter settings.

Only one variable was intentionally changed.

The issue is now considered:

> **Potentially resolved – monitor for recurrence.**

Because the failure is intermittent, there is no immediate way to prove that the driver update corrected it.

If the problem returns, that recurrence will itself become useful evidence.

---

## A Power Outage Hits Nora

The more significant incident occurred on Nora.

Earlier in the day, a power outage caused an unexpected shutdown.

When Nora was powered back on, the system repeatedly failed to boot normally. Several attempts resulted only in a black screen with a flashing white cursor.

After approximately four attempts, Nora eventually booted successfully.

Because Nora hosts much of AETHER's core infrastructure, this immediately became more important than an inconvenient desktop networking problem.

The first step after recovery was not to begin changing things.

It was to inspect the evidence.

---

## The Missing Boots

The systemd journal contained the previous long-running Nora session and the current successful boot.

It did **not** contain entries for the unsuccessful attempts.

The previous boot ended following the power interruption, while the next recorded boot was the successful recovery later that evening.

There were no intermediate boot IDs corresponding to the attempts that stopped at the flashing cursor.

This suggests that the unsuccessful boots failed before Linux reached the point where systemd-journald could establish a normal boot journal.

That narrowed the investigation toward an earlier portion of the boot process:

* Firmware and hardware initialization.
* Storage detection.
* Bootloader initialization.
* Early kernel startup.

The successful boot then provided another clue.

---

## An ATA Link Failure

Approximately eight minutes after Nora successfully booted, the kernel recorded an error involving the primary system drive:

```text
ata1.00: exception Emask 0x10
ata1.00: connection status changed
ata1: SError: { RecovComm Persist PHYRdyChg CommWake 10B8B DevExch }
ata1.00: failed command: READ FPDMA QUEUED
ata1: hard resetting link
```

The kernel subsequently recovered:

```text
ata1: SATA link up 3.0 Gbps
ata1.00: configured for UDMA/133
ata1: EH complete
```

The affected device was identified as Nora's primary SSD:

```text
/dev/sda
WD Blue SA510 2.5 1000GB
1 TB SATA SSD
```

Linux had lost communication with the drive while processing a read request, detected that the connection status had changed, performed a hard reset of the SATA link, and successfully restored communication.

This was much more interesting than the collection of ordinary ACPI and old-hardware warnings elsewhere in the boot log.

---

## Checking the SSD

Because a storage communication error can indicate either a failing drive or a problem elsewhere in the SATA path, SMART data was collected from the WD Blue SA510.

The overall SMART health assessment passed.

Several important attributes were clean:

```text
Reallocated_Sector_Ct    0
Grown_Bad_Blocks         0
Reported_Uncorrect       0
Command_Timeout          0
UDMA_CRC_Error_Count     0
```

The SMART error log also contained:

```text
No Errors Logged
```

The SSD has approximately 309 power-on hours and relatively little wear.

SMART also recorded one unexpected power loss, corresponding with the day's outage.

Nothing in the available SMART data currently provides strong evidence that the SSD media itself is failing.

---

## The Familiar SATA Cable

There is, however, another suspect.

The SATA cable.

This is not the first time Nora has experienced behavior suggesting a questionable SATA connection.

The cable had previously become suspicious during earlier troubleshooting, but because the system stabilized, it was never actually replaced.

That decision has now returned to the ticket queue.

The current kernel evidence is particularly consistent with a connection-level problem:

```text
connection status changed
```

followed by:

```text
hard resetting link
```

and then:

```text
SATA link up 3.0 Gbps
```

Combined with clean SMART health data and the previous history of SATA connectivity concerns, the physical SATA path is currently a stronger suspect than SSD failure.

Replacement SATA cables will be purchased.

The existing cable will finally be retired rather than receiving another opportunity to redeem itself.

---

## Backup Before Repair

The most important result of the incident is not identifying the cable.

It is the reminder that Nora has become important enough that a storage problem matters.

Nora currently hosts core AETHER infrastructure, Docker services, configuration, documentation-related systems, and virtual machines.

The system is currently running and the SSD is readable.

That makes **now** the correct time to back it up.

The immediate priority following this investigation is therefore to verify and expand the existing AETHER backups before performing unnecessary repairs or deeper storage testing.

Once the important data has been protected, the SATA data cable can be replaced and the connection monitored for additional ATA errors.

---

## Two Incidents, One Lesson

The Windows Ethernet problem and Nora's storage problem are technically unrelated.

Operationally, however, they demonstrated the same process.

For the Windows desktop:

> Connectivity failed.
> The obvious reset did not work.
> A reboot restored service.
> Logs revealed repeated hardware resets.
> Inspection revealed an extremely old driver.
> One corrective change was made.
> The system is now being monitored.

For Nora:

> A power outage caused an unexpected shutdown.
> Several boot attempts failed.
> The system eventually recovered.
> The failed boots occurred too early to leave normal journals.
> The successful boot revealed an ATA connection failure.
> SMART data did not indicate obvious SSD failure.
> Previous SATA cable concerns became relevant again.
> Backups were prioritized before further intervention.

Neither problem has been declared definitively solved.

That is intentional.

Sometimes the correct operational state is simply:

> **Potential cause identified. Corrective action taken or planned. Monitor for recurrence.**

---

## AETHER After Several Quiet Weeks

The gap between this log and the previous entry is itself somewhat representative of where AETHER is now.

There will still be new projects.

There will still be new services, experiments, migrations, and architecture.

But an operational environment also spends long periods simply existing.

Then the power goes out.

A network controller stops responding.

A SATA link resets.

A server refuses to boot.

And suddenly the value of monitoring, logs, documentation, backups, hardware inventory, and methodical troubleshooting becomes obvious.

AETHER does not need constant expansion to remain useful.

Sometimes the lab provides the lesson on its own.

---

## Final State

At the end of this incident and troubleshooting session:

* A Windows 10 Ethernet outage was traced to repeated Realtek PCIe GbE controller resets.
* Windows recorded 21 hardware resets during approximately 15 minutes of connectivity problems.
* Disabling and re-enabling the adapter did not restore connectivity.
* A complete reboot successfully restored the adapter.
* The Realtek controller was discovered to be using driver version `9.1.410.2015` from April 2015.
* The network driver was updated as the first corrective action.
* The Ethernet incident is considered potentially resolved and will be monitored for recurrence.
* A power outage caused an unexpected shutdown of Nora.
* Nora subsequently required several attempts before successfully booting.
* The failed boot attempts occurred before normal systemd journal initialization.
* Nora's successful boot later recorded an ATA bus/link error involving its primary WD Blue SA510 SSD.
* Linux successfully hard-reset the SATA link and restored communication.
* SMART reports the SSD as healthy with no reallocated sectors, grown bad blocks, reported uncorrectable errors, command timeouts, or logged SMART errors.
* The existing SATA cable remains the leading physical suspect due to both the current connection-status error and previous SATA troubleshooting history.
* Replacement SATA cables will be purchased.
* Backup and recovery work is being prioritized before additional storage troubleshooting.

The last AETHER log described learning how to live with infrastructure after it has been built.

Apparently part of living with infrastructure is occasionally having it wake up and choose to be difficult.

Fortunately, it also leaves logs.
