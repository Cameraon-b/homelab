
# AETHER Log #43 – Bringing Systems Back and Letting Agents Out

**Date:** November 4, 2026

AETHER has been relatively quiet on the infrastructure side lately.

Not inactive, certainly. Development on Nexus has continued, AI agents have become a larger part of the environment, and the lab is still providing plenty of opportunities to experiment with new technologies.

But the core infrastructure has largely been left alone to do its job.

That changed when the Windows Server evaluation finally reached its first expiration limit.

Around the same time, another project was taking shape: connecting Hermes, my AI engineering agent, to Discord so I could interact with it remotely without needing to sit at my desktop.

These were two very different exercises.

One involved recovering an existing system that had stopped operating.

The other involved extending an existing system into something considerably more accessible.

Both provided useful lessons about the increasingly interconnected nature of AETHER.

---

## The Windows Server Evaluation Finally Expires

WIN-DC01 is AETHER's Windows Server 2022 evaluation VM.

It runs on Nora, the Ubuntu Server host responsible for much of the lab's infrastructure, and provides Active Directory Domain Services and DNS for the `aether.lab` domain.

The evaluation has been running for some time, and I knew that eventually I would need to rearm the trial to continue using it.

Apparently, that day had arrived.

I initially discovered the problem when I could no longer connect to the server through TigerVNC.

Rather than immediately assuming that the VM itself was broken, I connected to Nora over SSH to investigate the state of the virtual machines.

Nora uses KVM/libvirt to manage the Windows environment, so the first step was straightforward:

```bash
sudo virsh list --all
```

The output was:

```text
Id   Name           State
----------------------------
-    WIN-CLIENT01   shut off
-    WIN-DC01       shut off
```

Both Windows virtual machines were powered off.

This was consistent with the suspected evaluation expiration, although the VM state alone did not establish the shutdown cause.

At least the problem was not an inaccessible hypervisor or an unresponsive Linux host.

Nora was operational.

The virtual machines simply needed attention.

---

## Starting the Wrong Virtual Machine

The next step should have been to start WIN-DC01.

Instead, I started WIN-CLIENT01.

```bash
sudo virsh start WIN-CLIENT01
```

Libvirt confirmed:

```text
Domain 'WIN-CLIENT01' started
```

I then checked the VNC display:

```bash
sudo virsh vncdisplay WIN-CLIENT01
```

The result was:

```text
127.0.0.1:0
```

This indicated that the VM's VNC console was available on display `:0`, corresponding to TCP port 5900.

I attempted to connect through TigerVNC, but something was not working as expected.

After another look at the VM list, the mistake became obvious.

```text
Id   Name           State
----------------------------
3    WIN-CLIENT01   running
-    WIN-DC01       shut off
```

I had started the client instead of the domain controller.

A simple mistake, but an instructive one.

The virtualization host was doing exactly what I had instructed it to do.

I had simply instructed it to start the wrong machine.

---

## Recovering WIN-DC01

With the mistake identified, I started the correct VM.

```bash
sudo virsh start WIN-DC01
```

The domain controller started successfully.

A subsequent check showed both Windows VMs running:

```text
Id   Name           State
----------------------------
3    WIN-CLIENT01   running
4    WIN-DC01       running
```

Meanwhile, Uptime Kuma began reporting that some of the monitored services were returning online.

That was encouraging.

It suggested that the domain controller was booting and restoring services, even though I had not yet regained console access.

The remaining problem was TigerVNC.

I checked the VNC display assigned to WIN-DC01:

```bash
sudo virsh vncdisplay WIN-DC01
```

The result was:

```text
:1
```

This was the missing piece.

WIN-DC01 was listening on VNC display `:1`, corresponding to TCP port 5901.

I had been trying to connect using port 5900.

That had worked previously, so I initially assumed it would still be correct.

However, libvirt can dynamically assign VNC display numbers depending on the order in which virtual machines start.

Because WIN-CLIENT01 had started first, it occupied display `:0`.

WIN-DC01 was assigned display `:1`.

The relationship was:

| Virtual Machine | VNC Display | TCP Port |
|---|---|---|
| WIN-CLIENT01 | `:0` | 5900 |
| WIN-DC01 | `:1` | 5901 |

Once I corrected the connection settings, TigerVNC successfully connected to the Windows Server console.

The lesson was simple:

> A previously valid connection setting is not necessarily a permanent configuration.

For future troubleshooting, `virsh vncdisplay` is a more reliable source of information than remembering which port worked last time.

---

## Rearming Windows Server

With console access restored, I could finally address the original problem.

Windows Server evaluation installations support a limited number of rearms, allowing the evaluation period to be extended without immediately reinstalling the operating system.

The relevant Windows licensing utility is `slmgr`.

The evaluation status and remaining rearm count can be inspected using:

```cmd
slmgr /dlv
```

The rearm operation itself uses:

```cmd
slmgr /rearm
```

The evaluation was successfully rearmed.

Following the rearm and recovery, WIN-DC01 returned to normal operation.

The services dependent on the Windows environment also came back online, with Uptime Kuma providing confirmation that monitored endpoints were recovering.

No rebuild was required.

No domain migration was necessary.

The existing Active Directory environment remained intact.

The incident was resolved by restoring the VM, reconnecting to its console, and extending the evaluation period.

This was also a useful reminder that evaluation licensing is an operational dependency.

The server can be technically healthy while still becoming unavailable because of licensing restrictions.

For a lab environment, that is manageable.

For production infrastructure, it would be an unacceptable surprise.

## A New Interface for Hermes

The other major development involved Hermes.

Hermes has been operating on Reeba as an AI engineering agent, primarily assisting with Nexus development and other technical work.

Until now, most interactions required sitting at the computer and using the local application.

That worked, but it created an obvious limitation.

If I had an idea while away from home, I either needed to remember it or wait until I returned to my computer.

I wanted to experiment with giving Hermes a messaging interface.

Discord seemed like a good candidate.

It supports bots, private servers, direct messaging, and persistent conversations across desktop and mobile devices.

More importantly, it would allow Hermes to remain on Reeba while I communicated with it remotely.

The architecture would be relatively simple:

```text
Discord Mobile App
        |
        v
Discord Platform
        |
        v
Hermes Discord Integration
        |
        v
Hermes Gateway
        |
        v
Reeba / AETHER
```

The phone would not be running Hermes.

It would simply provide another interface to an agent already running inside the lab.

## The Gateway Stops Connecting

I created the Discord bot and entered its token into the messaging configuration inside Hermes.

The application indicated that a restart was required.

After restarting, however, Hermes failed to reconnect.

The desktop application displayed:

```text
Error invoking remote method 'hermes:connection':
Error: Gateway draining (ensure_failed).
Use hermes gateway status for recovery.
```

Both Retry and Repair returned me to the same error.

Initially, I suspected that something had gone wrong with the token or that the new Discord configuration was preventing the gateway from starting correctly.

I considered removing the token manually to restore the previous working configuration.

Before making any changes, however, I checked the gateway directly from PowerShell.

```powershell
hermes gateway status
```

The result was more informative than the desktop error.

```text
✓ Gateway is running (PID: 19996)
  (Running manually, not as a system service)
```

The gateway was not actually stopped.

It was running, but it had recorded a Discord connection failure.

The health report identified the problem:

```text
discord: Discord rejected the connection because
privileged Gateway Intents are not enabled for
this bot in the Developer Portal.

Hermes is requesting:
- Message Content Intent
  (required to read message text)
```

This changed the diagnosis considerably.

The gateway process itself was alive.

Discord was refusing the connection because the bot was requesting a permission that had not been enabled.

---

## Understanding Discord Gateway Intents

Discord bots use Gateway Intents to specify which categories of events they need to receive.

Certain intents are considered privileged because they expose information that Discord restricts by default.

One of these is the Message Content Intent.

Without it, a bot may be unable to access the message text required for ordinary conversational interactions.

Hermes was requesting this capability, but the bot's configuration in the Discord Developer Portal did not permit it.

The solution was not to remove the token or reinstall Hermes.

Instead, I opened the Discord Developer Portal and navigated to:

```text
Applications
    |
    v
Hermes Application
    |
    v
Bot
    |
    v
Privileged Gateway Intents
    |
    v
Message Content Intent
```

I enabled Message Content Intent and saved the changes.

After restarting Hermes, the Discord connection issue was resolved.

The gateway was able to operate with the permissions it required.

This was an interesting example of a configuration problem that initially looked like an application failure.

The visible symptom was a gateway connection error.

The underlying issue was a missing permission in an external service.

The diagnostic output provided the distinction.

## Getting Hermes onto Discord Mobile

Fixing the gateway was only part of the process.

The next problem was that Hermes did not appear anywhere in my Discord mobile application.

I had configured the bot in Hermes and enabled the required Discord permissions, but that did not automatically make it available as a contact or server member.

Discord bot creation, installation, and messaging access are separate steps.

The bot needed to be properly installed and authorized within Discord before I could interact with it.

After completing the remaining Discord setup, Hermes became accessible through the mobile application.

I sent it messages from my phone.

It responded.

Hermes was now running on Reeba while I communicated with it through Discord.

That was a surprisingly satisfying moment.

A locally hosted AI agent had effectively become reachable through the same interface I might use to message another person.

And unlike a conventional chatbot, Hermes retained access to the engineering capabilities configured on its host system.

I asked Hermes whether it still had its usual capabilities through Discord.

It indicated that it did.

That does not necessarily establish that every conversation shares identical session context, but it suggests that the messaging interface is not fundamentally limiting the agent's available tools.

Further testing will establish how context and session persistence behave across the desktop and Discord interfaces.

## Securing the Discord Integration

Giving an AI agent remote messaging access introduces additional security considerations.

Hermes is not simply a conversational application.

It can potentially interact with files, execute commands, and modify systems within the permissions granted to it.

That makes Discord authentication and access restrictions particularly important.

For this integration, I configured the bot to remain private and restricted authorized interaction to my own Discord username/account.

The intention is that only I can issue instructions to Hermes.

The gateway is also currently running manually rather than as a Windows system service.

The status command reported:

```text
Running manually, not as a system service
```

Hermes supports installing the gateway as a Windows Scheduled Task using:

```powershell
hermes gateway install
```

That could eventually provide automatic startup when the host logs in.

For now, the priority is learning how the Discord integration behaves before expanding its autonomy or persistence.

The current access restrictions provide an initial layer of protection, but they are not a substitute for limiting the agent's operating-system permissions and requiring approval for sensitive actions.

Remote accessibility increases convenience.

It also increases the importance of understanding exactly what the agent is authorized to do.

## AETHER's Emerging AI Team

The Discord integration has also prompted me to reconsider how the different AI tools in AETHER should be used.

Hermes has primarily been focused on engineering work, particularly Nexus.

Mira, my OpenClaw-based agent, has been more closely associated with documentation, knowledge management, and maintaining context about the environment.

Meanwhile, ChatGPT and Codex remain useful for brainstorming, architectural discussions, programming, and working through technical questions.

Rather than expecting every agent to perform every function, I am beginning to envision a division of responsibilities.

| Agent | Primary Responsibility |
|---|---|
| Hermes | Engineering, implementation, infrastructure tasks, troubleshooting |
| Mira | Documentation, knowledge management, preserving project context |
| ChatGPT | Brainstorming, planning, learning, technical discussion |
| Codex | Software development, implementation, code review |

Nexus could eventually provide a common coordination layer between these systems.

Agents could receive tasks, report progress, and reference shared project information without requiring unrestricted access to one another.

For the moment, however, this remains an architectural direction rather than a completed system.

There is also the question of token consumption.

Autonomous agents can consume significant resources when allowed to operate continuously or recursively.

For the foreseeable future, Hermes will remain instruction-driven.

I will assign tasks when needed rather than allowing it to independently work through a queue indefinitely.

This approach also keeps me involved in the engineering process.

AETHER is not simply an environment I want AI to operate.

It is an environment I built to learn.

Delegating repetitive work is useful.

Delegating every interesting problem would defeat part of the purpose.

## From Local Tools to Remote Capabilities

The most interesting part of this development is not Discord itself.

It is the change in how I can interact with my own infrastructure.

Previously, working with Hermes meant being physically present at Reeba or establishing some form of remote desktop access.

Now I can open Discord on my phone and communicate with the agent directly.

That creates possibilities for a different workflow.

I could be away from home and remember something I wanted to investigate on Nora.

I could encounter an interesting technical problem at work and ask Hermes to prepare a lab experiment for later.

I could have an idea for Nexus while hiking and send it to Hermes before forgetting it.

Depending on the task and permissions, Hermes could investigate, prepare changes, or simply preserve the idea until I return.

The important distinction is that the agent remains inside AETHER.

Discord is only the communication layer.

This is another step toward treating the homelab as a collection of services and capabilities rather than a set of computers that require direct interaction.

## Two Problems, Two Different Lessons

The Windows Server recovery and Hermes integration were unrelated technically.

But they both demonstrated how much of systems administration involves understanding the boundaries between components.

In the Windows Server incident, the relevant components were:

```text
SSH
  |
  v
Ubuntu Server (Nora)
  |
  v
KVM / libvirt
  |
  v
VNC Console
  |
  v
Windows Server
  |
  v
Active Directory / DNS
```

The VM was running, but the console connection was using the wrong port.

The server was recoverable, but the evaluation needed to be rearmed.

The underlying infrastructure remained intact.

In the Hermes incident, the relevant components were:

```text
Discord Mobile
  |
  v
Discord Bot Installation
  |
  v
Discord Gateway Permissions
  |
  v
Hermes Gateway
  |
  v
Hermes Agent on Reeba
```

The Hermes gateway was running, but Discord rejected its requested permissions.

The bot existed, but it still needed to be made accessible through Discord.

In both cases, understanding which layer was failing prevented unnecessary changes to components that were already working.

## Closing Thoughts

AETHER continues to evolve in ways I did not necessarily anticipate when I first started building it.

Originally, the objective was to learn how computers communicate, how servers operate, how networks are administered, and how services can be deployed and maintained.

Those goals have not changed.

But the environment has grown into something more interesting.

There is now a Windows domain, a collection of Linux services, monitoring, documentation, remote access, development infrastructure, and increasingly capable AI agents.

And those systems are beginning to interact.

One evening I am troubleshooting why a Windows Server evaluation VM has shut itself down.

Another evening I am messaging an AI agent on my phone that is running on a computer in my house.

Both are part of the same learning process.

One teaches me how to recover infrastructure.
