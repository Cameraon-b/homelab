# AETHER Log #39 – A World Becomes a Place

**Date: July 27, 2026**

The next stage of the homelab began with a simple family goal.

Grayson and I already had a Minecraft world that mattered to us. We had built in it together, explored it separately, accumulated supplies, and gradually transformed it from a randomly generated landscape into a record of time spent together.

The problem was that the world remained tied to Cass.

When I opened the world and shared it over the local network, Grayson could join. When I closed Minecraft, the world disappeared with it. Cass was simultaneously my client, the host, and the machine responsible for keeping the world available.

That arrangement worked, but it imposed an important limitation:

The world only existed when I deliberately opened it.

Grayson could not enter unless I was already playing. I could not leave while he remained connected. The computer I used for music, development, AI experimentation, and general work also had to act as the Minecraft server.

The goal was not merely to create another Minecraft world.

The goal was to give our existing world an independent home.

## From Hosted Session to Dedicated Service

A Minecraft world shared through the game client is fundamentally dependent on the player hosting it.

The architecture looked like this:

```text
Cass
├── Minecraft client
├── World data
└── Temporary LAN host
        │
        └── Gray joins as a guest
```

Cass was not merely visiting the world.

Cass was the world.

If the game closed, the server closed. If Cass restarted, Grayson was disconnected. If I wanted to use the machine for something else, the shared session ended.

A dedicated server changes that relationship.

The server process owns the world and runs independently. Player computers become clients that connect to it over the network.

The intended architecture was:

```text
Reeba
└── Dedicated Minecraft server
        │
        ├── Cass connects as a player
        └── Gray connects as a player
```

Neither player computer would be responsible for hosting.

Cass could disconnect.

Gray could disconnect.

The other player could remain.

Even if neither of us was logged in, the world would continue to exist on Reeba, waiting for the next connection.

This was the conceptual objective behind the entire project.

## Choosing Reeba

Most permanent AETHER services live on Nora.

Nora hosts BookStack, Uptime Kuma, GLPI, Nginx Proxy Manager, Memos, RustDesk, and other infrastructure services. It is the central Linux server and the operational heart of AETHER.

Minecraft did not belong there.

Nora has limited memory and already carries responsibilities that matter to the rest of the environment. Adding a game server would compete with infrastructure services and blur the boundary between two very different purposes.

Minecraft is not infrastructure for AETHER.

It is an application used by the family.

Reeba was a better fit.

Reeba has substantially more processing power than Nora and already serves as a capable Windows workstation. It could host the server without placing additional pressure on the machines responsible for documentation, monitoring, remote access, and lab administration.

This created a useful separation of roles:

```text
Nora
Infrastructure services

Cass
Development, AI, music, and primary workstation

Reeba
Family application hosting

Gray
Minecraft client and personal workstation
```

The decision was not based only on available hardware.

It established a boundary.

AETHER infrastructure would remain on Nora.

The Minecraft world would receive a separate home on Reeba.

## Installing Docker Desktop

The server would run inside a Docker container.

Docker was already familiar from Nora, but Reeba runs Windows rather than Ubuntu Server. This required Docker Desktop and the Windows Subsystem for Linux.

The first attempt did not work.

Docker Desktop reported that virtualization was unavailable.

Task Manager showed otherwise:

```text
Virtualization: Enabled
```

The processor and firmware were capable of virtualization, but the required Windows components were not fully installed.

Windows Features revealed that both of the following were disabled:

```text
Windows Subsystem for Linux
Virtual Machine Platform
```

Those features were enabled and the computer was restarted.

Docker Desktop still did not function correctly.

The remaining requirement was a WSL Linux distribution.

Ubuntu was installed under WSL, providing the Linux environment Docker Desktop expected. After another restart, Docker Desktop finally opened successfully.

The installation was verified with:

```powershell
docker version
```

Both the client and server portions responded.

The standard test container was then launched:

```powershell
docker run hello-world
```

For a moment, the command appeared to be stuck.

Docker was actually downloading the image.

Once the download completed, the container ran and printed the expected confirmation message.

Docker Desktop, WSL2, and Linux containers were operational on Reeba.

## Building the Minecraft Container

A dedicated directory was created for the service:

```text
Docker
└── minecraft
    ├── compose.yaml
    └── data
```

The Compose configuration defined the Minecraft server container, accepted the Minecraft end-user license agreement, published the default Java Edition server port, and mounted the data directory so that the world would persist outside the container.

The basic architecture became:

```text
Windows 11
    │
    ▼
Docker Desktop
    │
    ▼
WSL2 Linux environment
    │
    ▼
Minecraft server container
    │
    ▼
Persistent world data on Reeba
```

The container was started with Docker Compose.

Images were downloaded.

The server generated its files.

The logs showed the Minecraft server initializing.

A new test world appeared inside the persistent data directory.

Cass opened Minecraft and connected to Reeba’s local network address.

The connection succeeded.

I entered a newly generated world running inside a Linux container on Reeba while playing from the Minecraft client on Cass.

The server existed independently of the client.

That was the first major success.

## Understanding the Administrative Boundary

The server was running, but the next task was granting operator privileges.

I entered the container shell and attempted to run:

```text
op camcam9076
```

The shell responded:

```text
/bin/sh: op: not found
```

The mistake was not the Minecraft command.

The mistake was where it had been entered.

I was speaking to the Linux shell inside the container rather than the Minecraft server console.

The container contained multiple layers:

```text
Linux shell
    │
    └── Minecraft Java process
```

Minecraft commands such as `op`, `gamemode`, and `gamerule` are not Linux executables. They must be sent to the running Minecraft server.

The container image provided an RCON command-line utility for this purpose.

From PowerShell, the operator command was issued through the container:

```powershell
docker exec -i minecraft-server rcon-cli op camcam9076
```

The server confirmed that the account had been made an operator.

The same process was later used for Grayson.

This distinction was an important lesson:

Entering a container does not necessarily place the administrator inside the application running within it.

The operating-system shell and the application console are separate administrative contexts.

## Authentication and Online Mode

During testing, Minecraft occasionally displayed an authentication-server error.

The dedicated server was running with online authentication enabled.

In this mode, joining players are validated through Microsoft and Mojang’s authentication services. This protects the relationship between usernames and player identities and prevents someone from simply choosing another player’s name.

Disabling online mode could avoid dependence on external authentication, but it would introduce other consequences.

Player identities are represented internally by UUIDs. Online and offline mode may calculate those identities differently. Changing the mode after a world has already been used can make a returning player appear to be a new person, separating them from their previous inventory, location, advancements, and other player-specific data.

The server was already functioning.

The authentication issue was intermittent.

Online mode was therefore left enabled.

This preserved the normal identity model and avoided creating unnecessary migration work.

## Preparing to Move the Real World

The generated world proved that the server worked.

It was not the world that mattered.

The important save still lived on Cass.

The migration plan was straightforward:

1. Stop the Minecraft container.
2. Preserve the generated test world.
3. Copy the existing family world from Cass to Reeba.
4. Place it inside the Minecraft data directory.
5. Ensure the imported directory used the expected world name.
6. Restart the server.
7. Confirm that the dedicated server loaded the original world.

The container was stopped cleanly.

Docker reported the container as exited.

The generated world directory needed to be renamed so it could remain as a backup:

```powershell
Rename-Item world world-test
```

Instead, Windows returned:

```text
Access denied
```

## The Folder That Would Not Let Go

The error initially appeared to be a permissions problem.

Ownership was checked.

Permissions were inspected.

Attributes were reviewed.

Administrative commands were attempted, including tools for taking ownership and resetting access-control entries.

Everything indicated that the account had permission to modify the directory.

The container was not running.

Docker showed it as exited.

Yet Windows still refused to rename the folder.

This pointed toward a different category of problem.

The directory was not protected by its security permissions.

It was still being held open.

Docker Desktop, WSL, or another process associated with the container environment had retained a handle to the world directory even after the Minecraft container stopped.

The distinction mattered:

```text
Permission problem:
The account is not authorized to modify the object.

File-handle problem:
The account is authorized, but another process still has the object open.
```

Changing ownership cannot release an active file handle.

Resetting access-control entries cannot persuade a process to stop using a directory.

The permissions had never been the real issue.

Windows was restarted.

The restart terminated the remaining Docker and WSL processes and released their handles.

After the reboot, the rename worked immediately.

The generated server world became:

```text
world-test
```

The original family world was copied from Cass and placed into the data directory as:

```text
world
```

The files were now ready.

## Starting the Imported World

The container was started again.

In theory, the Minecraft server should detect the directory named `world` and load it instead of generating a new one.

The server initialized.

Cass connected.

The loading screen disappeared.

I entered the world.

I was standing in the same location where I had last saved while playing on Cass.

The landscape was correct.

The structures were present.

The inventory and player state remained intact.

The migration had succeeded.

This was the moment when the project became real.

The world had moved from one computer to another without ceasing to be the same world.

Cass no longer owned it.

Reeba did.

## Two Clients, One Independent World

The final test required both players.

I connected from Cass.

Grayson connected from Gray.

The world ran on Reeba.

The architecture was now:

```text
                  Atlas
             Ethernet switch
                    │
        ┌───────────┼───────────┐
        │           │           │
      Cass        Gray        Reeba
      Client      Client      Server
        │           │           │
        └───────────┴───────────┘

```

Cass was one player.

Gray was another player.

Reeba held the world independently of both.

Neither client was hosting.

Neither client controlled the other player’s ability to remain connected.

The server had become a persistent meeting place on the local network.


The clients did not need to communicate directly with each other.

Both communicated with the server.

Atlas was no longer merely an eight-port device that created additional Ethernet connections.

It was holding up the shared network experience.

The name fit.

## A World Independent of Its Players

The most significant conceptual change was the separation between the world and the people visiting it.

Previously:

```text
No host player
=
No world
```

Now:

```text
No connected players
≠

```

The server exists whether anyone is currently using it.

The world is persistent.

It can be entered independently.

Grayson can build while I am doing something else.

This changes the emotional character of the save.

## Troubleshooting as Architectural Discovery

Like previous AETHER projects, the Minecraft server did not fail in one simple way.

The project crossed several layers:

* Windows virtualization
* Optional Windows features
* WSL installation
* Docker Desktop startup
* Linux container execution
* Image downloading
* Docker Compose configuration
* Persistent volume mapping
* Minecraft server initialization
* Mojang authentication
* RCON administration
* Local firewall behavior
* LAN connectivity
* World directory naming
* Windows file permissions
* Open file handles
* Save migration
* Player identity
* Multiplayer validation

Each issue revealed the boundary between two parts of the system.

The virtualization error revealed that firmware support and operating-system configuration are separate requirements.

The `op` command failure revealed that a container shell and an application console are different interfaces.

The folder rename failure revealed that authorization and resource locking are different problems.

The successful world migration revealed that the server process and its persistent data can be separated.

The two simultaneous clients revealed the full client-server model.

Troubleshooting did not merely fix the system.

It exposed its architecture.
