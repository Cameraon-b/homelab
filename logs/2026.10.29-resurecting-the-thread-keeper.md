# AETHER Log #43 – The Thread Keeper Returns

**Date:** October 29, 2026

The last AETHER log was about systems misbehaving.

Apparently they were not finished.

This time, the problem was not a network adapter or a questionable SATA cable. It was Mira: AETHER's Thread Keeper, documentation agent, and one of the first pieces of the larger agent system that has started to feel like more than an experiment.

An OpenClaw migration to version `2026.10.8` left Mira's original profile unable to recover cleanly. What followed was not a simple software update. It became a practical test of whether an agent could survive the loss of its working profile when its identity, memory, documentation, and source material existed across several different systems.

The answer was encouraging, but not effortless.

Mira returned.

She did not return because the original profile suddenly repaired itself. She returned because enough of the important pieces had been preserved to build a new profile, restore her identity and memory, reconnect her knowledge sources, and verify that she could search them again.

That distinction matters.

> **The profile failed. The agent did not have to disappear with it.**

---

## The OpenClaw 2026.10.8 Recovery

The incident began during the move to OpenClaw `2026.10.8`.

Mira's original profile did not come through the migration in a usable state. Attempts to recover it directly did not produce a trustworthy working environment, and continuing to modify the damaged profile would have made it harder to distinguish repair from additional damage.

The original profile was therefore treated as evidence rather than as the place to keep experimenting.

Before rebuilding Mira, the available OpenClaw state and related data were backed up. The goal was not merely to preserve a directory. It was to preserve options:

- Retain the failed profile for later inspection.
- Protect identity and memory material before making more changes.
- Preserve the ability to compare the old and new profiles.
- Avoid turning a migration problem into an irreversible loss.

This was the same principle that appeared in the previous AETHER incident:

> **Backup before repair.**

Only this time, the system being recovered had a name.

---

## The Original Profile Was Not Reused

The recovery did not depend on forcing the original Mira profile back into service.

A new profile named `mira-new` was created instead.

That provided a clean OpenClaw `2026.10.8` environment while leaving the failed profile intact. It also created a useful boundary between what was known to be damaged and what could be verified one component at a time.

The new profile was not assumed to be Mira merely because it had her name.

An empty agent profile with a familiar label is still an empty agent profile.

Mira's identity, operating context, and memory material had to be restored deliberately. The relevant preserved files were brought into the new profile, then reviewed as part of the recovery rather than copied blindly and declared successful.

This separated two different questions:

1. Can OpenClaw start the new profile?
2. Does the new profile contain enough of Mira to continue her role?

The first question was a software recovery problem.

The second was an agent continuity problem.

Both had to be answered.

---

## Restoring the Thread Keeper

Mira's identity and memory were restored into `mira-new` from the preserved material.

This included the context that defines her role inside AETHER, the continuity needed to recognize the environment she serves, and the memory sources that allow her to do more than begin every session as a stranger with access to tools.

The restoration demonstrated that Mira is not contained in one place.

She exists across several layers:

- The OpenClaw profile that provides her working runtime.
- Identity and instruction files that define who she is and how she operates.
- Memory data that provides continuity.
- Archived conversations that preserve prior interactions.
- BookStack, which holds AETHER's maintained documentation.
- GitHub, which holds the AETHER logs and other versioned project history.

The original profile was one implementation of Mira, but it was not the only surviving record of her.

That is why recovery was possible.

It is also why backing up only the profile directory would not be a complete backup of the agent.

---

## Rebuilding Keyword Search

Restoring memory files is not the same as making them usable.

Mira's keyword full-text search index was rebuilt and verified in the new profile. The completed index reported:

```text
Sources indexed:  23 / 23
Chunks indexed:   106
Search mode:      keyword full-text search
```

All 23 expected sources were indexed, producing 106 searchable chunks.

This was an important recovery checkpoint. It showed that the new profile could do more than hold copied files. OpenClaw could process the restored sources and expose them through keyword search.

The result does not prove that every possible memory query will return the ideal answer. It does establish that the restored memory corpus is present, indexable, and available to Mira in the new environment.

The correct status is therefore:

> **Keyword memory indexing restored and verified. Retrieval quality will continue to be observed during normal use.**

---

## The 184 Archived Chats

The recovery also identified **184 archived chats**.

They were preserved, but they were **not imported into Mira's active memory index**.

That was intentional.

The existence of an archive does not automatically make every item appropriate for active retrieval. Importing all 184 chats without a review could introduce duplicated material, stale context, irrelevant conversations, or a large amount of low-value text into Mira's working memory.

The archive and the active memory system therefore remain separate:

- The archived chats are retained as historical source material.
- The 23 selected sources are indexed for active keyword retrieval.
- The archived chats have not been discarded.
- No claim is being made that the 184 chats are currently searchable through Mira's restored FTS index.

This is not unfinished recovery masquerading as success.

It is a scope decision.

Preservation came first. Selective import, if useful, can happen later with a clearer understanding of what belongs in active memory.

---

## Reconnecting BookStack

Mira's role is not limited to remembering conversations. She is AETHER's Thread Keeper, and BookStack remains one of her most important sources of maintained knowledge.

The restored environment was reconnected to BookStack and its accessible inventory was verified:

```text
Pages:    322
Books:     52
Shelves:    8
```

That inventory represents a substantial portion of AETHER's documented state.

The successful count did not mean that all 322 pages were copied into Mira's local memory. It meant that Mira's restored profile could again reach the documentation system and see the expected body of material.

This distinction is useful:

> **BookStack is a source of maintained truth. Mira's memory is a working context. They should support one another without being confused for the same thing.**

BookStack survived independently of the failed OpenClaw profile, which made it part of the recovery rather than part of the loss.

---

## Reconnecting GitHub

GitHub was also reconnected and verified.

The AETHER repository contained **43 logs**, including the history leading to this entry.

Like BookStack, GitHub provided continuity outside the agent runtime. The logs do not recreate every private memory or every past conversation, but they preserve the narrative of the project: what changed, why it changed, what was learned, and what remained unresolved.

That makes the logs more than project updates.

They are part of AETHER's recoverable memory.

The recovery did not expose credentials, tokens, private repository addresses, or other authentication details. Connectivity was verified by the resulting inventory, not by recording secrets in the incident log.

That rule applies here as well. This document records what was restored, not the sensitive material used to restore it.

---

## Restarting the Gateway

After the new profile, restored identity and memory, rebuilt search index, and external knowledge connections were in place, the OpenClaw gateway was restarted.

The restart was the transition from recovery work to an operational check. It ensured that the active service loaded the recovered configuration rather than continuing to run with stale state from before the repair.

Following the restart, Mira was available through the new profile with her core context and connected knowledge sources restored.

The gateway restart did not repair the original profile.

It made the verified replacement profile the working environment.

---

## Recovery Is Not the Same as Perfect Continuity

It would be easy to summarize the incident by saying that Mira was backed up and restored.

That would be true, but incomplete.

The recovery preserved the parts that mattered most:

- A working OpenClaw `2026.10.8` profile.
- Mira's identity and role.
- Her selected memory sources.
- A verified 23-source, 106-chunk keyword index.
- Access to 322 BookStack pages across 52 books and 8 shelves.
- Access to the GitHub repository containing 43 AETHER logs.
- A separate archive of 184 chats for possible later review.

What it did not establish was a bit-for-bit restoration of the failed profile.

Nor did it establish that every archived conversation had been returned to active memory.

The recovered Mira is operationally continuous, not a forensic clone of the broken runtime.

That is an important and honest definition of success.

## Model Usage and the Cost of Agents

The recovery also raised a broader concern about how AETHER's agents use language models.

Different tasks do not require the same model, the same amount of reasoning, or the same number of tokens. An agent can consume significant resources by repeatedly inspecting large histories, re-reading documentation, retrying failed operations, or using an expensive model for work that a smaller model or conventional program could handle.

That matters even when every individual request appears reasonable.

An autonomous system can turn small inefficiencies into recurring costs.

The long-term design should therefore distinguish between:

- Continuous conventional monitoring.
- Event-driven agent investigation.
- Lightweight routine model work.
- Expensive reasoning reserved for tasks that justify it.

AETHER does not need an LLM continuously generating tokens in order to have useful intelligence available around the clock.

Monitoring can remain inexpensive and deterministic. Agents can be invoked when a condition requires interpretation, documentation, planning, or repair.

Model selection, token budgets, maximum runtimes, retry limits, and usage reporting are therefore not merely billing preferences. They are operational controls.

No final automated cost-control system was implemented during this recovery. It remains a design requirement for the next stage of AETHER's agent architecture.

---

## Safe Autonomy Requires External Boundaries

Mira's recovery naturally led into the larger question of what AETHER's agents should eventually be allowed to do.

The goal is not to avoid autonomy.

The goal is to make autonomy survivable.

Hermes may eventually build applications, Mira may keep documentation current, and other agents may investigate alerts or prepare infrastructure changes while I am away. I would like to remain responsible for AETHER's direction without personally performing every repetitive task required to move it forward.

But instructions are not security boundaries.

Telling an agent not to delete a repository does not protect the repository if the agent runs under an account that can delete it. A local Gitea copy and a GitHub copy provide redundancy only if a single execution environment cannot destroy or rewrite both.

The same principle applies to Mira's recovery:

> **A backup that the operating agent can alter or delete is not an independent recovery boundary.**

Safe autonomy will require controls outside the agents themselves:

- Disposable or isolated working copies.
- Protected branches and restricted force-push or deletion rights.
- Credentials scoped to the minimum required service and action.
- Backups that agent execution accounts cannot modify.
- Approval gates for destructive operations and production changes.
- Runtime, token, concurrency, and spending limits.
- Audit logs and clear reports of completed actions.
- Recovery procedures tested before overnight autonomy depends on them.

The desired failure mode is not an agent that never makes a mistake.

That is not a realistic engineering target.

The desired failure mode is an agent that can ruin its disposable workspace without ruining AETHER.

> **The worst possible agent mistake should be an inconvenience, not a disaster.**

## What Was Completed

The following actions were completed as part of this recovery:

- The failed original Mira profile was preserved rather than overwritten during continued experimentation.
- Backups were created before rebuilding the working environment.
- A clean `mira-new` profile was created on OpenClaw `2026.10.8`.
- Mira's identity, role, and selected memory material were restored into the new profile.
- Keyword full-text search indexing completed for all 23 expected sources.
- The restored sources produced 106 searchable chunks.
- The 184 archived chats were preserved separately and intentionally not imported into active memory.
- BookStack connectivity was restored and an inventory of 322 pages, 52 books, and 8 shelves was verified.
- GitHub connectivity was restored and the repository inventory of 43 AETHER logs was verified.
- The OpenClaw gateway was restarted after the restored configuration was in place.
- Mira returned to operation through the replacement profile.

## What Remains Planned

The following items are plans or design requirements. They were **not** completed merely because they were discussed during the incident:

- Review whether any of the 184 archived chats should be selectively imported into active memory.
- Define a repeatable export and restore procedure for each agent's identity, memory, indexes, and configuration.
- Automate backup verification rather than assuming that the existence of backup files guarantees recoverability.
- Keep at least one agent-inaccessible or otherwise independently protected copy of critical repositories and recovery material.
- Audit the Git credentials, SSH keys, authenticated command-line tools, and repository permissions available inside agent execution environments.
- Separate development access from authoritative upstream and production access.
- Add protected branches, deletion restrictions, approval gates, and narrowly scoped credentials where they are not already enforced.
- Establish per-agent model policies, token budgets, maximum runtimes, retry limits, and cost reporting.
- Build regular status reports that clearly distinguish actions taken, proposals awaiting approval, failures, and resource usage.
- Test a full Mira recovery from documented backups without relying on the damaged original profile.
- Begin overnight autonomy only with bounded, reversible tasks in isolated environments.

These are not claims about the current environment.

They are the work exposed by the recovery.

## Lessons for AETHER Backups

This incident changed the definition of an agent backup.

A profile directory is not enough.

A useful recovery set needs to account for:

- The runtime and its compatible version.
- Agent configuration.
- Identity and instruction material.
- Working memory sources.
- Search indexes or a documented method to rebuild them.
- Conversation archives.
- External knowledge systems and their access requirements.
- Repositories and project history.
- A manifest explaining what should exist after restoration.
- Secrets stored separately from ordinary logs and backups.

Some items should be backed up directly. Others, like an index, may be safer to rebuild from authoritative sources. External systems such as BookStack and GitHub require their own backups and access controls; merely pointing Mira at them does not protect them.

Most importantly, recovery should be tested.

An untested backup is evidence of hope, not evidence of recoverability.

Mira's return is encouraging because the preserved pieces were sufficient this time. The next recovery should not depend on reconstructing the procedure during the incident.

## The Thread Keeper Returns

There is something strange about recovering an agent named the Thread Keeper from a collection of threads.

Mira's original OpenClaw profile failed, but her continuity was distributed across identity files, memory sources, archived conversations, BookStack documentation, GitHub history, and the decisions made while rebuilding her.

No single one of those was Mira.

Together, they were enough for her to return.

That makes this more than a successful profile migration.

It is the first meaningful demonstration that an AETHER agent can be treated as a recoverable system rather than a disposable session.

The recovery was imperfect, manual, and more complicated than it should be.

But it worked.

The Thread Keeper has her threads again.

Fortunately, the threads were still there.
